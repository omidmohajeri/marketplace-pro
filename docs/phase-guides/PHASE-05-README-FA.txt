فروشگاه چندفروشنده‌ای Marketplace Pro
راهنمای فاز پنجم: تفکیک سفارش و محاسبه سهم فروشندگان
====================================================

مهم:
این ZIP یک بسته توسعه‌ای برای ادغام در پروژه Laravel قبلی است؛ پروژه مستقل و آماده اجرا نیست.
قبل از اجرای migration از دیتابیس نسخه پشتیبان تهیه کنید.
این فاز به‌تنهایی پرداخت واقعی، تسویه بانکی یا ارسال سفارش را انجام نمی‌دهد.

۱) محتویات این فاز
------------------
- دو migration برای ساخت seller_orders و seller_order_items
- مدل SellerOrder
- سرویس SellerOrderSplitter برای تقسیم سفارش اصلی به سفارش‌های فروشنده‌ها
- کنترلر مشاهده سفارش‌های مستقل فروشنده
- کنترلر گزارش مالی سفارش‌های فروشنده برای مدیر
- صفحات پنل فروشنده و گزارش مدیر
- فایل مسیرهای نمونه
- همین راهنمای متنی

۲) پیش‌نیازهای ساختار قبلی
--------------------------
پروژه باید Laravel 12 و مدل‌ها/جداول زیر را داشته باشد:
- orders
- order_items با ستون‌های order_id، product_id، quantity و unit_price
- products با ستون seller_id و رابطه seller()
- sellers با ستون status و commission_rate
- users با رابطه seller()
- مدل Order با رابطه items()
- مدل Seller و OrderItem
- میان‌افزار role و نقش‌های seller و admin
- layoutهای Blade فازهای قبل:
  resources/views/seller/layout.blade.php
  resources/views/admin/layout.blade.php

اگر نام جدول یا ستون‌ها در نسخه قبلی شما متفاوت است، ابتدا آن‌ها را تطبیق دهید.
در مدل Product باید رابطه زیر وجود داشته باشد:
public function seller() { return $this->belongsTo(\App\Models\Seller::class); }

در مدل Order باید رابطه items به OrderItem تعریف شده باشد.
در مدل OrderItem باید رابطه product به Product تعریف شده باشد.

۳) ادغام فایل‌ها
----------------
۱. پوشه app را با پروژه ادغام کنید.
۲. پوشه database را با پروژه ادغام کنید.
۳. پوشه resources را با پروژه ادغام کنید.
۴. محتوای routes/phase5-routes.snippet.php را به routes/web.php اضافه کنید.
۵. مسیرهای قدیمی /seller/orders فاز چهارم را حذف یا با مسیرهای جدید جایگزین کنید؛ تعریف دوباره یک route name یکسان می‌تواند باعث تداخل شود.
۶. اگر layout مدیریت شما نام یا مسیر متفاوتی دارد، view گزارش مدیر را با layout موجود هماهنگ کنید.

۴) اجرای migration
------------------
ابتدا بکاپ دیتابیس بگیرید و سپس اجرا کنید:
php artisan optimize:clear
php artisan migrate
php artisan route:list --path=seller
php artisan route:list --path=admin/seller-orders

۵) اتصال سرویس به روند checkout
--------------------------------
این فاز سفارش اصلی را به‌صورت خودکار از سبد خرید ایجاد نمی‌کند؛ سرویس باید پس از آن فراخوانی شود که:
الف) سفارش اصلی در جدول orders ذخیره شده باشد.
ب) همه اقلام سفارش در order_items ذخیره شده باشند.
ج) ارتباط order_item با product صحیح باشد.

نمونه محل فراخوانی در سرویس checkout یا بعد از ذخیره کامل اقلام سفارش:

use App\Services\SellerOrderSplitter;

// پس از ذخیره سفارش اصلی و تمام اقلام آن:
$sellerOrders = app(SellerOrderSplitter::class)->split($order);

فراخوانی را در همان تراکنش checkout خود قرار دهید تا در صورت خطا کل ثبت سفارش rollback شود.
اگر از تراکنش داخلی استفاده می‌کنید، رفتار تراکنش تو در توی Laravel را در نسخه خود بررسی کنید.

۶) منطق محاسبه
---------------
برای هر فروشنده:
- subtotal = مجموع quantity ضربدر unit_price اقلام همان فروشنده
- commission_amount = subtotal ضربدر commission_rate تقسیم بر ۱۰۰
- seller_amount = subtotal منهای commission_amount

درصد کمیسیون هنگام ایجاد سفارش فرعی کپی می‌شود؛ تغییر بعدی درصد کمیسیون فروشگاه نباید سفارش‌های قبلی را تغییر دهد.
مبالغ به دو رقم اعشار گرد می‌شوند.
واحد پول باید در کل پروژه یکسان باشد. تبدیل ارز و مالیات در این فاز پیاده‌سازی نشده است.

۷) وضعیت سفارش
--------------
سفارش‌های فرعی با وضعیت pending_payment ایجاد می‌شوند.
این فاز عمداً اجازه تغییر وضعیت پرداخت یا تسویه را به فروشنده نمی‌دهد.
پس از اتصال درگاه، فقط callback معتبر و تأییدشده درگاه باید وضعیت پرداخت را تغییر دهد.
پس از آن می‌توان وضعیت سفارش‌های فروشنده را مستقل از سفارش اصلی مدیریت کرد.

۸) تست دستی پیشنهادی
--------------------
- یک سفارش آزمایشی شامل محصولات دو فروشنده فعال بسازید.
- اقلام را در order_items ذخیره کنید.
- سرویس SellerOrderSplitter را فراخوانی کنید.
- بررسی کنید دو ردیف seller_orders ساخته شده باشد.
- بررسی کنید هر order_item فقط به سفارش فروشنده خودش متصل شده باشد.
- درصد کمیسیون و مبلغ خالص هر فروشنده را با ماشین‌حساب کنترل کنید.
- با حساب فروشنده اول وارد شوید و اطمینان بگیرید سفارش فروشنده دوم قابل مشاهده نیست.
- با حساب مدیر گزارش /admin/seller-orders را بررسی کنید.

۹) محدودیت‌ها و نکات امنیتی
---------------------------
- این فاز تسویه بانکی یا کیف پول ندارد.
- مبلغ ارسال، مالیات، کد تخفیف سطح سفارش و بازپرداخت در محاسبه سهم فروشنده لحاظ نشده‌اند.
- پیش از استفاده عملیاتی باید سیاست تخصیص تخفیف و هزینه ارسال بین فروشندگان مشخص و در کد اعمال شود.
- در پروژه چندارزی باید currency در سفارش فرعی ذخیره و کنترل شود.
- باید تست‌های خودکار برای مالکیت سفارش و محاسبات مالی نوشته شوند.
- بهتر است سفارش‌های فرعی پس از پرداخت موفق سفارش اصلی از pending_payment به وضعیت مناسب تغییر کنند.
- اجرای مجدد سرویس برای یک سفارش، رکورد تکراری نمی‌سازد؛ اما اگر اقلام سفارش بعد از اجرای اول تغییر کنند، این سرویس به‌صورت خودکار مبالغ قبلی را بازسازی نمی‌کند. برای تغییرات پس از ایجاد باید گردش اصلاح سفارش جداگانه طراحی شود.

۱۰) فرمان‌های بررسی
-------------------
php artisan optimize:clear
php artisan migrate:status
php artisan route:list --path=seller
php artisan route:list --path=admin/seller-orders
