فروشگاه چندفروشنده‌ای Marketplace Pro
راهنمای فاز ششم: زیرساخت درگاه پرداخت و تأیید تراکنش
====================================================

این بسته زیرساخت عمومی پرداخت را اضافه می‌کند. درگاه واقعی هنوز متصل نشده است؛
برای اتصال واقعی باید Adapter مخصوص شرکت پرداخت انتخابی و اطلاعات پذیرنده آن اضافه شود.
این بسته عمداً پرداخت موفق جعلی تولید نمی‌کند.

۱) محتویات
----------
- migration جدول payment_attempts
- مدل PaymentAttempt
- قرارداد PaymentGateway
- سرویس PaymentService
- کنترلر آغاز پرداخت و callback
- Adapter نمونه غیرفعال ExampleGateway
- تنظیمات config/payments.php
- Provider اتصال قرارداد به Adapter
- فایل مسیرهای نمونه
- همین راهنمای متنی

۲) پیش‌نیازها
-------------
- Laravel 12 و فازهای قبلی پروژه
- جدول orders با ستون‌های user_id، grand_total، currency و status
- مدل Order
- مسیر orders.show برای صفحه جزئیات سفارش
- کاربر احراز هویت‌شده
- تنظیم Provider پرداخت در پروژه

۳) ادغام فایل‌ها
----------------
۱. پوشه app، config و database را با پروژه ادغام کنید.
۲. محتوای routes/phase6-routes.snippet.php را به routes/web.php اضافه کنید.
۳. Provider را در bootstrap/providers.php ثبت کنید، اگر پروژه آن را خودکار کشف نمی‌کند:
   App\Providers\PaymentServiceProvider::class,
۴. اگر مسیر orders.show نام دیگری دارد، redirectهای PaymentController را اصلاح کنید.
۵. migration را اجرا کنید:
   php artisan optimize:clear
   php artisan migrate

۴) تنظیم محیط
-------------
این مقادیر نمونه را در .env قرار دهید:
PAYMENT_GATEWAY=example
PAYMENT_CURRENCY=IRR
PAYMENT_MERCHANT_ID=
PAYMENT_API_URL=
PAYMENT_CALLBACK_TTL=30

درگاه example عمداً غیرفعال است. تا زمان نصب Adapter رسمی، شروع پرداخت خطا می‌دهد.
این رفتار برای جلوگیری از ثبت پرداخت جعلی طراحی شده است.

۵) اتصال درگاه واقعی
--------------------
برای هر شرکت پرداخت باید کلاس مستقلی بسازید که PaymentGateway را پیاده‌سازی کند.
متد createPayment باید:
- مبلغ را از PaymentAttempt دریافت کند، نه از فرم مرورگر.
- درخواست را با کلید محرمانه سرور به API رسمی ارسال کند.
- شناسه authority را روی PaymentAttempt ذخیره کند.
- فقط URL امن HTTPS درگاه را برگرداند.

متد verifyCallback باید:
- authority و شناسه تلاش پرداخت را تطبیق دهد.
- از API رسمی درگاه، وضعیت تراکنش را استعلام کند؛ به پارامتر success مرورگر اعتماد نکند.
- مبلغ و واحد پول را با رکورد PaymentAttempt تطبیق دهد.
- در صورت موفقیت، آرایه استاندارد زیر را برگرداند:
  ['success' => true, 'amount' => مبلغ تأییدشده, 'reference' => 'کد پیگیری واقعی']
- در هر حالت دیگر success=false برگرداند یا خطای معتبر ایجاد کند.

پس از ساخت Adapter، اتصال آن را در PaymentServiceProvider جایگزین ExampleGateway کنید.
کلیدها را در کد منبع یا Git قرار ندهید؛ فقط در .env سرور نگهداری کنید.

۶) شروع پرداخت
---------------
فرم صفحه سفارش باید به این مسیر POST ارسال کند:
route('payments.checkout', $order)
در فرم از @csrf استفاده کنید.
کنترلر مالکیت سفارش را بررسی می‌کند و مبلغ را از دیتابیس می‌خواند.

۷) امنیت و نکات مهم
-------------------
- تغییر وضعیت سفارش به paid فقط پس از verify سمت سرور انجام می‌شود.
- وضعیت پرداخت از ورودی مرورگر پذیرفته نمی‌شود.
- callback دارای URL امضاشده است.
- مبلغ پرداخت‌شده با مبلغ ثبت‌شده در دیتابیس مقایسه می‌شود.
- callback تکراری به‌صورت idempotent کنترل می‌شود.
- برای پرداخت واقعی باید امضای callback یا استعلام server-to-server مطابق مستندات همان درگاه اجرا شود.
- در محیط عملیاتی HTTPS، محدودیت نرخ درخواست، ثبت رویداد امنیتی و مانیتورینگ ضروری است.
- بازپرداخت، پرداخت چندمرحله‌ای، مالیات و هزینه ارسال هنوز پیاده‌سازی نشده‌اند.
- پس از پرداخت موفق، باید وضعیت SellerOrderهای فاز پنجم نیز از pending_payment به وضعیت مناسب تغییر کند؛ این اتصال در این فاز انجام نشده است.
- برای درگاه‌هایی که مبلغ را به ریال یا تومان می‌خواهند، تبدیل واحد باید دقیق و فقط در Adapter انجام شود.
- پیش از انتشار، تست خودکار برای پرداخت موفق، پرداخت ناموفق، مبلغ ناهماهنگ، callback تکراری و تلاش برای پرداخت سفارش دیگران بنویسید.

۸) تست اولیه
------------
php artisan optimize:clear
php artisan migrate:status
php artisan route:list --name=payments

توجه: چون Adapter نمونه غیرفعال است، تست واقعی پرداخت تا اتصال درگاه منتخب امکان‌پذیر نیست.
